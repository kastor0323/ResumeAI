### Q2. AI 추천 연산이나 외부 API 연동 등 지연 시간이 긴 고부하 연산을 수행할 때 메인 API 서버의 성능 저하를 방지하기 위해 어떤 설계를 도입하셨습니까?

리액티브 논블로킹 클라이언트인 `WebClient`를 도입하고, `ThreadPoolTaskExecutor`를 통해 AI 전용 비동기 스레드 풀을 격리함으로써 톰캣 스레드 고갈 리스크를 원천 차단했습니다.

Flask 기반 AI 추천 서버에 리밸런싱 비율 연산을 요청하는 과정은 수 초 이상의 대기가 발생하는 고부하 작업이었습니다. 기존의 동기식 `RestTemplate`을 사용하면 톰캣의 메인 스레드가 블로킹되어 전체 웹 서비스가 마비될 위험이 있었습니다. 이를 해결하기 위해 비동기 논블로킹 방식의 `WebClient`로 통신 구조를 전환했습니다. 이에 더해 `@Async("aiExecutor")`를 선언하고 별도의 비동기 스레드 풀을 구성하여 AI 통신 프로세스를 메인 API 스레드 풀과 물리적으로 격리했습니다. 그 결과 AI 연산이 아무리 지연되거나 동시 요청이 쏠리더라도, 핵심 메인 API 서버의 톰캣 작업 스레드 차단 시간을 0ms로 완벽히 방어할 수 있었습니다.

### Q3. 데이터베이스 설계 과정에서 무결성 오류나 정합성 붕괴 문제를 해결하기 위해 어떤 노력을 하셨습니까?

학술적 지식을 실제 아키텍처에 대입하여 1단계부터 3단계 데이터베이스 정규화를 순차적으로 수행하였으며, JPA Cascade 및 고아 객체 삭제 옵션을 최적화하여 참조 무결성을 완전히 보장했습니다.

프로젝트 초기에는 단일 테이블 위주로 구성되어 다수의 중복 컬럼과 이상 현상이 발생했습니다. 저는 반복 그룹을 제거하는 1정규화부터 부분 함수 종속성을 제거하는 2정규화, 이행적 함수 종속성을 제거하는 3정규화를 차례로 적용해 `User`, `Account`, `Portfolio` 등 독립된 도메인 테이블로 분리했습니다. 또한 외래키 관계에서 종속 데이터가 남아 발생하는 정합성 붕괴를 해결하기 위해, 연관관계 매핑 시 `CascadeType.ALL`과 고아 객체 제거 옵션인 `orphanRemoval = true`를 선언했습니다. 이를 통해 부모 레코드가 삭제될 때 자식 데이터도 안전하게 함께 삭제되는 구조를 확립하여 DB 레벨의 물리적 무결성과 정합성을 완벽하게 확보했습니다.

### Q4. 네트워크 재전송이나 사용자의 동시 다발적 요청으로 발생할 수 있는 중복 주문 문제를 방지하기 위해 어떤 멱등성 전략을 취하셨습니까?
* **핵심 질문 요지**: 분산 시스템에서의 분산 락 활용 및 네트워크 신뢰성 대응(At-least-once) 역량 검증

**[답변 초안]**
Redis 분산 락을 이용한 1차 검증과 데이터베이스 레벨의 UNIQUE 제약조건을 결합한 이중 안전망을 통해 주문 접수의 멱등성을 엄격하게 보장했습니다.

네트워크 재전송 등 분산 환경에서 동일 주문이 중복으로 접수되는 것은 금융 시스템에서 치명적인 사고로 이어집니다. 이를 원천 차단하기 위해 주문 API 요청이 유입될 때 `userId`와 `clientOrderId`를 결합한 복합키를 생성하여 Redis에서 1차로 중복 조회를 수행하고 동시에 락을 획득하도록 구현했습니다. 이에 더해 Redis 장애나 예외 상황에 대비하여 RDB 테이블에 동일한 복합키 기반의 `UNIQUE` 복합 제약조건을 이중 안전망으로 구축했습니다. 이 같은 이중 멱등성 필터 아키텍처를 통해 불필요한 DB 조회 오버헤드를 대폭 낮추고, 어떤 네트워크 불안정 상태에서도 동일한 주문이 중복 처리되는 정합성 이상 현상을 철저히 예방할 수 있었습니다.

### Q5. 대용량 배치를 처리하는 과정에서 데이터 누락이나 지연이 발생한 버그를 어떻게 해결하셨는지 기술적 원인과 함께 설명해 주십시오.
* **핵심 질문 요지**: 대용량 배치 최적화 및 쿼리 튜닝, 논리적 트러블슈팅 역량 검증
* **예상 발화 시간**: 약 1분 12초 (공백 포함 511자)

**[답변 초안]**
대용량 배치 작업 도중 처리 상태 값 변경으로 인해 데이터 조회 오프셋이 밀려 누락이 발생하던 문제를 규명하고, Offset 기반 페이지네이션을 Cursor-based 페이지네이션으로 전환하여 해결했습니다.

약 75,000건의 대용량 Outbox 데이터를 처리하는 배치 실행 중 일부 데이터가 누락되는 현상이 감지되었습니다. 원인을 추적한 결과, 배치 스케줄러가 데이터를 조회하고 처리 완료 상태로 값을 업데이트할 때마다 전체 조회 대상 목록의 오프셋이 앞으로 당겨져 다음 페이지 조회 시 레코드 일부를 건너뛰는 상태 유실 버그였습니다. 이를 해결하기 위해 조회 대상이 변할 때 정렬 오프셋을 잃어버리는 `OFFSET` 조회를 완전히 걷어내고, 직전 페이지에서 마지막으로 처리한 레코드의 ID를 조건식으로 전달하는 `id > last_processed_id` 형태의 Cursor-based 방식으로 리팩토링했습니다. 이를 통해 조회 대상을 고정하여 누락율을 0%로 만들었습니다.

### Q6. 비동기 메시징 시스템인 Kafka를 사용하면서 메시지의 처리 순서와 특정 파티션 트래픽 쏠림 문제를 어떻게 고려하여 설계하셨습니까?
* **핵심 질문 요지**: 이벤트 드리븐 아키텍처(EDA) 내 순서 보장 전략 및 트래픽 분산 설계 역량 검증
* **예상 발화 시간**: 약 1분 12초 (공백 포함 513자)

**[답변 초안]**
메시지의 논리적 순차 처리를 보장하기 위해 `userId` 및 `symbol`을 파티션 키로 설계하였으며, 특정 파티션에 트래픽이 집중되는 핫 파티션 현상에 대처하기 위한 복합 키 아키텍처 방안을 수립했습니다.

주문 접수와 체결 등의 금융 이벤트는 순서가 보장되어야 하므로 주문 요청 토픽에는 종목명인 `symbol`을 키로 지정하고, 체결 토픽에는 `userId`를 파티션 키로 설정하여 동일 대상의 데이터가 항상 물리적으로 동일한 파티션에 순차 적재되도록 설계했습니다. 나아가 특정 종목에 급격한 거래 요청이 집중되어 파티션 병목이 우려되는 상황을 선제적으로 예방하고자, 단일 키 대신 `symbol + (userId % N)`과 같은 해시 복합 파티션 키를 구성하여 데이터를 파티션에 균등하게 분배하는 고도화 설계를 준비했습니다. 이를 매칭 엔진 내부의 분산 메모리 큐로 병렬 처리하여 순서 보장과 트래픽 분산이라는 두 마리 토끼를 모두 잡는 방안을 확보했습니다.

### Q7. Write-behind 패턴을 통해 I/O 병목을 해결할 경우 Redis나 메인 서버가 다운되었을 때 발생할 수 있는 데이터 유실 문제에 대해 어떤 대비책을 세우셨습니까?
* **핵심 질문 요지**: 인메모리 캐시 장애 대처 능력 및 이벤트 드리븐 시스템에서의 데이터 복구(Event Replay) 전략 검증
* **예상 발화 시간**: 약 1분 11초 (공백 포함 505자)

**[답변 초안]**
Redis 유실로 인한 정합성 손상을 방지하기 위해 Kafka의 수동 오프셋 커밋(Manual Acknowledgment) 정책을 채택하고, 이벤트 리플레이를 통한 정합성 강제 맞춤 복구 시나리오를 설계했습니다.

실시간 계산된 미실현 손익(PnL)을 Redis 캐시에 즉시 반영하고 DB에는 100건 단위로 일괄 배치 업데이트하는 Write-behind 방식을 사용했습니다. 따라서 DB 반영 전에 서버가 꺼지면 캐시 데이터가 소실되는 심각한 리스크가 있었습니다. 이에 대응하기 위해 데이터가 실제 관계형 데이터베이스에 정상적으로 저장 및 커밋 완료된 건에 대해서만 메시지 브로커인 Kafka의 컨슈머 오프셋을 수동으로 커밋하도록 제어 로직을 구현했습니다. 이를 통해 뜻하지 않은 인프라 중단이 발생하더라도, 재부팅 시 수동 커밋되지 않은 지점부터 Kafka 메시지를 다시 읽어 들여 손실된 Redis 캐시 데이터를 완벽하게 재구성하고 원장과의 일관성을 100% 유지하게끔 복구 안전망을 수립했습니다.

### Q8. 금융 서비스의 보안성과 안전한 세션 관리를 위해 토큰 인프라를 어떻게 설계하셨습니까?
* **핵심 질문 요지**: 인증/인가 보안 모델 수립 및 인메모리 DB를 활용한 세션 관리 제어권 확보 역량 검증
* **예상 발화 시간**: 약 1분 10초 (공백 포함 496자)

**[답변 초안]**
Access Token과 Refresh Token 이중화 구조를 구축하고, Redis의 TTL 및 Blacklist 관리 방식을 채택하여 탈취 위험을 축소하고 서버의 강제 세션 제어권을 확보했습니다.

사용자의 민감한 계좌 정보와 포트폴리오 데이터를 보호하기 위해 Spring Security 기반의 JWT 인증 체계를 도입했습니다. 탈취 시의 피해를 최소화하고자 유효기간 15분의 Access Token과 7일의 Refresh Token으로 이중화하여 발급했습니다. 특히 사용 기간이 긴 Refresh Token은 인메모리 캐시인 Redis에 관리하고 TTL(Time-To-Live)을 7일로 바인딩하여 만료 시 자동 삭제되도록 구현했습니다. 더불어 사용자의 수동 로그아웃이나 이상 세션 감지 시 즉각 토큰을 무효화할 수 있도록, Redis 내에 해당 Access Token을 남은 만료 시간만큼 Blacklist로 저장하여 통과를 차단하는 전략을 수립했습니다. 이를 통해 무상태성 토큰 아키텍처의 한계를 극복하고 실시간 통제력을 확보했습니다.

### Q10. 본부 기술지원 직무를 수행하게 된다면, 프로젝트 진행 중 발생했던 스프링 빈 Context 충돌과 같은 인프라/빌드 레벨의 장애를 어떻게 해결해 나갈 것입니까?
* **핵심 질문 요지**: 프레임워크 생명주기 및 빌드 프로필 격리 이해도, 본부 IT 기술지원에 필요한 신속한 예방/해결 능력 검증
* **예상 발화 시간**: 약 1.5분 (공백 포함 513자)

**[답변 초안]**
Spring Boot의 빌드 프로필 기반 Context 격리 기법을 적용하여 인프라 실행 환경의 논리적 경계를 명확히 분리함으로써 컴포넌트 충돌 및 배포 설정 장애를 사전에 통제하고 신속히 대응하겠습니다.

실제 거래 감지 시스템 배포 당시, Web API 전용 모듈 인스턴스에서 원치 않는 컨슈머 빈인 `@KafkaListener`가 컨텍스트 로딩 시 자동으로 기동되어 불필요하게 메시지를 당겨오며 에러가 터지는 현상이 발생했습니다. 저는 인스턴스의 컴포넌트 스캔 주기와 로직 실행 시점을 분석하여, 환경 설정을 물리적으로 쪼개는 `@Profile("worker")` 조건부 빈 등록 기법을 적용했습니다. 이를 통해 API 모듈과 Worker 모듈이 각자의 타깃 설정만 정확히 읽어 들이도록 통제하여 배포 충돌을 원천 해결했습니다. 제가 본부 IT 기술지원 부서에 투입된다면, 빌드 생명주기와 설정 프로필을 철저히 검증하여 환경 불일치로 인한 시스템 장애를 철저히 조기 진단하고 예방할 것입니다.
