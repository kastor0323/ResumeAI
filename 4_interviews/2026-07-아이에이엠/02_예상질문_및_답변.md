  * [성과] AI 연동 구간의 지연이 전체 시스템의 API 응답 지연으로 전파되는 구조적 위험을 차단하여 톰캣 블로킹 0ms 유지.

### Q10. 경진대회 출품작에서 데이터 무결성을 위해 1NF부터 3NF까지 정규화를 진행했다고 하셨는데, 정규화가 무조건 성능 향상을 보장하지 않으며, 조인(Join) 증가로 인한 조회 성능 저하가 발생할 수 있습니다. 이를 어떻게 극복했나요?
* **출제 의도:** 데이터베이스 설계 시 트레이드오프(Trade-off)를 이해하고 있으며, 반정규화(Denormalization) 또는 대체 솔루션을 적용할 수 있는지 확인
* **[나의 답변 초안]** 
  * [문제 인지] 3NF까지 분리하면서 `RebalancingStock`과 `User` 정보를 매 요청마다 조인해야 하여 조회 비용이 상승하는 트레드오프 발생.
  * [해결 행동] (1) 자주 변경되지 않는 이행 종속 정보는 Application Layer에서 **Redis 캐싱**을 활용해 DB 조인 횟수를 줄임. (2) 조회 성능 저하가 치명적인 통계 집계 페이지에서는 제한적으로 반정규화를 적용하거나 CQRS 패턴을 적용하여, 쓰기 중심의 정규화된 DB와 조회 중심의 인덱싱된 복제 DB(Read-only Replica)를 이원화해 극복함.

### Q11. 75,000건의 대용량 배치 처리 버그 해결 사례에서, Offset 기반 페이지네이션의 오프셋 밀림 현상이 구체적으로 왜 발생했으며, Cursor-based로 변경했을 때 누락이 방지된 원리는 무엇인가요?
* **출제 의도:** 대량 데이터 청크(Chunk) 처리 및 페이징 성능, DB 커서 메커니즘에 대한 명확한 기술적 이해도 검증
* **[나의 답변 초안]** 
  * [오프셋 밀림 원인] 배치 작업 중에 상태값을 `READY`에서 `SENT`로 변경함. Offset 기반 조회 (`LIMIT 100 OFFSET 100`) 시, 앞선 100건이 처리되어 상태값이 `SENT`로 빠져나가기 때문에 DB 내 조회 대상 모수가 줄어듦. 따라서 `OFFSET 100`을 적용하면 조회 대상이 한 단계 앞으로 당겨져, 아직 처리되지 않은 중간의 100건이 누락되는 버그 발생.
  * [Cursor-based 해결 원리] 페이지 번호(`OFFSET`) 대신 고유 식별자인 ID를 기준점(Cursor)으로 두고 검색함 (`WHERE id > last_processed_id LIMIT 100`).
  * [결과] 레코드 상태 변경이나 중간 데이터 추가/삭제와 상관없이, 마지막 처리된 ID 이후의 레코드만 순차 탐색하기 때문에 데이터 누락이 원천적으로 차단됨.

  * [체력 관리] 매주 3회 운동 루틴을 유지하는 것이 오히려 두뇌 회전과 집중력을 높여 장기 프로젝트의 총 개발 시간을 줄여준다는 것을 깨달았기에, 아무리 바쁜 시기에도 최소한의 리프레시 시간을 지켜 완성도 높은 품질을 방어함.

## 4. 자소서 기반 심층 꼬리 질문 (약점 방어)

### Q8. 경진대회 출품작에서 데이터 무결성을 위해 1NF부터 3NF까지 정규화를 진행했다고 하셨는데, 정규화가 무조건 성능 향상을 보장하지 않으며, 조인(Join) 증가로 인한 조회 성능 저하가 발생할 수 있습니다. 이를 어떻게 극복했나요?
* **출제 의도:** 데이터베이스 설계 시 트레이드오프(Trade-off)를 이해하고 있으며, 반정규화(Denormalization) 또는 대체 솔루션을 적용할 수 있는지 확인
* **[나의 답변 초안]** 
  * [문제 인지] 3NF까지 분리하면서 `RebalancingStock`과 `User` 정보를 매 요청마다 조인해야 하여 조회 비용이 상승하는 트레드오프 발생.
  * [해결 행동] (1) 자주 변경되지 않는 이행 종속 정보는 Application Layer에서 **Redis 캐싱**을 활용해 DB 조인 횟수를 줄임. (2) 조회 성능 저하가 치명적인 통계 집계 페이지에서는 제한적으로 반정규화를 적용하거나 CQRS 패턴을 적용하여, 쓰기 중심의 정규화된 DB와 조회 중심의 인덱싱된 복제 DB(Read-only Replica)를 이원화해 극복함.

### Q9. 75,000건의 대용량 배치 처리 버그 해결 사례에서, Offset 기반 페이지네이션의 오프셋 밀림 현상이 구체적으로 왜 발생했으며, Cursor-based로 변경했을 때 누락이 방지된 원리는 무엇인가요?
* **출제 의도:** 대량 데이터 청크(Chunk) 처리 및 페이징 성능, DB 커서 메커니즘에 대한 명확한 기술적 이해도 검증
* **[나의 답변 초안]** 
  * [오프셋 밀림 원인] 배치 작업 중에 상태값을 `READY`에서 `SENT`로 변경함. Offset 기반 조회 (`LIMIT 100 OFFSET 100`) 시, 앞선 100건이 처리되어 상태값이 `SENT`로 빠져나가기 때문에 DB 내 조회 대상 모수가 줄어듦. 따라서 `OFFSET 100`을 적용하면 조회 대상이 한 단계 앞으로 당겨져, 아직 처리되지 않은 중간의 100건이 누락되는 버그 발생.
  * [Cursor-based 해결 원리] 페이지 번호(`OFFSET`) 대신 고유 식별자인 ID를 기준점(Cursor)으로 두고 검색함 (`WHERE id > last_processed_id LIMIT 100`).
  * [결과] 레코드 상태 변경이나 중간 데이터 추가/삭제와 상관없이, 마지막 처리된 ID 이후의 레코드만 순차 탐색하기 때문에 데이터 누락이 원천적으로 차단됨.
