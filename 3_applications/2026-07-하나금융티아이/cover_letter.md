### 2. [자기소개] 본인에 대해 자유롭게 기술해주시기 바랍니다. (500~1000자)

["두 번 확인하고, 한 번에 완성한다" — 사전 점검으로 신뢰를 쌓는 개발자입니다]

한편 개발을 장기간의 마라톤으로 여기다 보니, 초반에 의욕만 앞세워 쉴 틈 없이 몰입하다가 후반부에 집중력이 떨어지는 한계를 겪은 적이 있습니다. 완성도 높은 결과물은 순간의 몰아치기가 아니라 꾸준히 유지되는 컨디션에서 나온다는 것을 깨닫고, 이후로는 웨이트 트레이닝, 풋살 등 운동으로 온오프 밸런스를 의식적으로 관리하기 시작했습니다. 그 결과 강행군 일정에서도 끝까지 몰입력을 유지하며 완주할 수 있었고, 이는 단기간의 집중력이 아니라 장기 근속을 전제로 한 체력 관리의 중요성을 스스로 체득하는 계기가 되었습니다.

### 3. [역량기술] 본인이 관심 있는 IT 분야 혹은 관련 경험을 자유롭게 기술해 주십시오. (500~1000자)

[원장 불일치 0건으로 증명한 데이터 정합성]

저는 '데이터 정합성을 지키는 백엔드 아키텍처'에 가장 큰 관심을 가지고 있으며, 이를 주식 매수/매도 이상거래 감지 시스템 개발 경험으로 직접 검증했습니다.

이 프로젝트는 주문 접수부터 매칭, 원장 기록, 정산까지 이어지는 거래 시스템에서 대량의 거래 이벤트를 유실·중복 없이 처리하고 잔고 데이터의 신뢰성을 상시 검증해야 하는 과제를 안고 있었습니다. 저는 전체 5개 서비스 중 Trading API Layer와 Risk Management 모듈을 전담했습니다.

먼저 클라이언트 주문을 Kafka로 비동기 발행해 API 응답 지연을 최소화하고, (userId, clientOrderId) 기준 Redis 락과 DB Unique 제약을 이중으로 적용해 네트워크 재전송 상황에서도 중복 처리를 차단했습니다. 또한 ledger_entry를 단일 진실 공급원으로 삼아 잔고 불일치를 원천 차단하는 구조를 설계했고, 다중 리스크 인스턴스 환경에서는 userId·symbol 단위 Redis 분산 락으로 동시 체결 시 발생하는 경쟁 조건을 방지했습니다. 개발 중에는 75,000건 이상의 대용량 배치 처리 시 Offset 기반 페이지네이션이 레코드를 누락시키는 버그를 발견해, ID 비교 기반 Cursor 페이지네이션으로 교체해 누락률 0%를 달성하기도 했습니다.

그 결과 원장과 잔고 데이터 간 불일치를 0건으로 검증했고, 75,000건의 원장 엔트리와 10,016건의 정산 결과를 누락 없이 처리했습니다. 이 경험을 통해 대용량 트래픽 환경에서 데이터 정합성을 지키는 것이 금융 시스템의 핵심 경쟁력임을 체감했고, 장애 허용도가 낮은 하나금융티아이의 서비스 환경에서도 이 역량을 곧바로 적용할 수 있다고 자신합니다.
