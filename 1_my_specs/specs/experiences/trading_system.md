# 📖 상황 (Situation)
주문 접수부터 매칭, 원장 기록, 정산까지 이어지는 트레이딩 코어 백엔드(TradingGate) 개발 프로젝트를 2인(BE)이 진행했습니다. 그중 저는 진입 관문인 **Trading API Layer**와 비동기 이벤트를 통해 체결을 책임지는 **Risk Management Module**의 전체 설계 및 구현을 전담했습니다. "안정적인 이벤트 처리"와 "검증 가능한 돈의 이동"이라는 가장 핵심적인 도메인 문제를 해결하는 것이 목표였습니다.

# 🎯 과제 (Task)
1. **신뢰성 있는 주문 인입**: 클라이언트 요청을 중복/누락 없이 안전하게 체결 파이프라인으로 연결 (멱등성 보장).
2. **실시간 리스크 제어**: 고빈도로 발생하는 체결 이벤트를 기반으로 실시간 리스크 평가 및 제어를 100ms 이내에 수행.
3. **완벽한 정합성 보장**: 동시에 발생하는 대규모 트랜잭션 하에서 분산 환경의 데이터 정합성(동시성 문제 및 이벤트 누락)을 100% 보장.

# 🚀 행동 (Action)
*   **API Layer 멱등성 및 아키텍처 격리**: Trading API 단계에서 도메인 DB를 직접 건드리지 않는 CQRS-ish 패턴을 설계하고, Redis 분산 락과 DB UNIQUE 제약조건을 활용한 이중 멱등성 방어벽을 구축해 클라이언트의 중복 주문 요청을 원천 차단했습니다.
*   **Kafka 기반 역할 분리 및 장애 국소화**: 전체 시스템을 5개의 런타임 프로필(api, worker, risk, clearing, projection)로 철저히 분리했습니다. 일례로 api 프로필은 Kafka Producer 역할만 수행하도록 애노테이션 조건부 등록을 통해 Listener 빈(Bean)을 비활성화, 불필요한 이벤트 소비 및 결합 리스크를 제거했습니다.
*   **대용량 배치 및 동시성 제어 고도화**: Redis 기반의 Write-Behind 캐싱(100건 단위 Bulk Update)을 적용하여 DB I/O 부하를 최적화했습니다. 그 과정에서 발생한 Outbox 이벤트 누락 버그(Pagination 오프셋 문제)를 '커서 기반(Cursor-based) 페이징'으로 고도화하여 타개했고, Risk Consumer 멀티 인스턴스의 갱신 충돌 문제는 Kafka 파티션 라우팅과 Redis 분산 락(timeout 5초, 최대 3회 재시도)을 결합해 논리적/물리적 배타성을 완벽히 구현했습니다.
*   **원장 중심 SSOT(Single Source of Truth) 설계**: `ledger_entry`를 변경할 수 없는 불변의 원장 기록(SSOT)으로 세우고, `account_balance`를 조회 전용 Projection으로 분리 설계하여 장애 지점 파악과 데이터 복구를 획기적으로 단순화했습니다.

# 🏆 결과 (Result)
*   아키텍처 설계와 동시성 제어 적용을 통해 **75,000건의 대용량 Ledger 엔트리 배치 처리 과정에서 이벤트 누락 0건**을 검증해냈습니다.
*   `ledger_entry`와 `account_balance` 간의 **데이터 불일치 현상(recon_diff)을 0건으로 통제**하며 핀테크 등급 수준의 시스템 신뢰성을 입증했습니다.
*   All-in-K8s 데모 환경을 성공적으로 구축하고 K6 부하 테스트(Smoke, Soak, Burst)를 완수하여, 긴급 리스크 감지 및 제어 이벤트가 부하 상황에서도 **100ms 이내에 안정적으로 처리**됨을 대시보드로 증명해 냈습니다.
