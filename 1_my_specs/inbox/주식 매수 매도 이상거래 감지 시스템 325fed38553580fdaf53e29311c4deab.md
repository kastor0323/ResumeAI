## 📖 프로젝트 소개

TradingGate Backend는 **주문 접수 → 매칭 → 원장 기록 → 잔고 → 정산 → 대사**를 하나의 흐름으로 연결한 트레이딩 코어 백엔드입니다.

단순한 주문 API 구현을 넘어, 두 가지 핵심 문제를 해결하는 것에 집중했습니다.

- **거래 이벤트를 어떻게 안정적으로 처리할 것인가**
- **돈의 이동을 어떻게 검증 가능한 구조로 유지할 것인가**

이를 위해 `ledger_entry`를 **SSOT(Single Source of Truth)** 로 두고, `account_balance`를 Projection으로 분리하는 원장 중심 아키텍처를 설계했습니다.

## 📌 **Trading API Layer**

클라이언트와 매칭 엔진 사이에 위치하는 진입 관문으로, 주문의 유효성을 검증하고 Kafka를 통해 안전하게 전달하는 역할입니다. **이 단계에서는 어떠한 도메인 DB도 직접 건드리지 않습니다.**

### **① 신규 주문 API**

- `POST /api/orders` — clientOrderId, symbol, side, price, quantity, timeInForce 수신
- 필수 필드 검증 → 심볼 유효성 확인(tick/step 규칙) → 유저 권한 체크 순차 수행
- Kafka `orders.in` 토픽에 **symbol을 key로 발행** → 동일 심볼은 항상 같은 파티션으로 라우팅
- API 응답은 '접수 완료' 수준으로 즉시 반환, 실제 체결 상태는 조회 API로 확인하는 **비동기 패턴** 적용

### **② 주문 취소 API**

- `POST /api/orders/cancel` — clientOrderId 또는 orderId 기반 취소 요청
- 이미 FILLED/CANCELED 상태 주문은 DB 조회 후 즉시 반환 → 불필요한 Kafka 발행 방지
- `CancelOrderCommand`를 `orders.in`에 발행(key=symbol)하여 매칭 워커가 오더북에서 제거

### **③ 멱등성 처리 *(핵심 설계 포인트)***

- `(userId, clientOrderId)` 복합키 기반 중복 요청 방지
- **Redis 1차 체크**: 이미 pending인 요청은 이전 결과 즉시 반환
- **DB UNIQUE 제약으로 2차 안전망** 확보 — Kafka까지 도달하더라도 매칭 워커에서 중복 무시
- at-least-once 환경에서도 exactly-once 수준의 비즈니스 결과 보장

### **④ 주문/체결 조회 API**

- `GET /api/orders`, `GET /api/trades` — userId, 기간, 심볼 필터링 지원
- Trading DB(Projection)를 조회 전용으로 활용 — **CQRS-ish 패턴**으로 읽기/쓰기 부하 분리

## 📌 **Risk Management Module**

매칭 엔진이 발행하는 `trades.executed` 이벤트를 소비하여 원장을 기록하고, 실시간으로 리스크를 평가·제어하는 시스템의 **"안전 관리 두뇌"** 역할입니다.

### **① 실시간 포지션 & PnL 계산 (B-1)**

- Kafka Consumer Group `risk-engine` — `trades.executed`를 userId key로 소비하여 **같은 유저 이벤트 순서 보장**
- Redis 분산 락(`lock:position:{userId}:{symbol}`, timeout 5초, 최대 3회 재시도)으로 **동시성 제어**
- BUY: 수량 증가 + 가중평균 단가 재계산 / SELL: 실현손익 계산 후 수량 감소
- `unrealized_pnl = 현재 포지션 수량 × (현재가 - 평균단가)` 미실현 손익 실시간 계산
- **Write-behind 패턴** 적용: 메모리 연산 후 100건 단위 DB Bulk Update로 I/O 부하 최소화
- Redis 캐시(`position:{userId}:{symbol}`, TTL 30분) → DB 미스 시에만 DB 조회

### **② 리스크 정책 평가 (B-2)**

사용자/심볼 단위 리스크 한도 **4종 실시간 평가**:

| 한도 유형 | 계산 방식 | 기본값 |
| --- | --- | --- |
| NOTIONAL | |포지션 수량| × 현재가 (총 노출도) | - |
| POSITION_SIZE | |수량| 기준 최대 포지션 | 1,000주 |
| DAILY_LOSS | 당일 누적 실현손익 | 초기 자본 -30% |
| MARGIN_RATIO | 자본 / 위험노출 | 총 노출 20% |
- `risk-config.yml`로 모든 임계값 **동적 조정 가능**한 유연한 정책 구조 설계

### **③ 리스크 제어 이벤트 발행 (B-3)**

위험 상황 감지 시 **Outbox 패턴**으로 `risk.commands` 토픽에 제어 이벤트 발행:

- `BLOCK_USER` — 특정 유저 거래 전면 차단
- `CANCEL_ORDERS` — 특정 유저/심볼 전체 미체결 주문 취소
- `MARGIN_CALL` — 증거금 부족 경고
- `REDUCE_ONLY` — 포지션 축소만 허용 모드 전환

key = userId로 발행하여 같은 유저 제어 이벤트 순서 보장, **긴급 이벤트 100ms 이내 처리** 보장

### **④ 이상 거래 감지 / 서킷 브레이커 (B-4)**

실시간 이상 패턴 **4종 감지**:

| 패턴 유형 | 감지 조건 |
| --- | --- |
| PRICE_SPIKE | 5분간 ±10% 이상 가격 변동 |
| ORDER_FLOOD | 1초에 100개 이상 주문 폭증 |
| REPEATED_CANCEL | 동일 주문 5회 이상 반복 취소 |
| VOLATILITY_BREACH | 변동성 임계값 초과 |

심각도(LOW/MEDIUM/HIGH/CRITICAL) 분류 후 조치 자동화:

- **CRITICAL**: 해당 심볼 status → HALTED, `risk.commands` 발행
- **HIGH**: 특정 계정 BLOCK + 강제 취소

## 🐛 트러블 슈팅

### 🔴 트러블슈팅 #1 — Outbox 페이지네이션 버그

#### 문제

대용량 배치 처리(75,000건 이상) 중 Outbox Publisher가 일부 이벤트를 누락하는 현상 발생

#### 원인 분석

Outbox Publisher가 `status = PENDING` 레코드를 **페이지 오프셋 기반**으로 조회할 때, 처리 완료(SENT)로 상태가 변경된 레코드들로 인해 오프셋이 밀려 다음 페이지 일부를 건너뛰는 문제. 소규모에서는 재현되지 않아 대용량 배치에서만 발견됨.

#### 해결 방법

조회 쿼리를 **오프셋 기반 → 커서 기반** (`id > last_processed_id`) 페이지네이션으로 변경. 처리 완료 여부와 무관하게 id 순서로 진행하므로 레코드 누락 원천 차단.

#### 결과

대용량 배치(75,000 ledger_entry)에서 Outbox 발행 **누락 0건** 달성. 배치 처리 안정성 확보.

### 🔴 트러블슈팅 #2 — 포지션 동시성 문제

#### 문제

Risk Consumer 다중 인스턴스 환경에서, 동일 userId의 `trades.executed` 이벤트가 서로 다른 인스턴스에 동시 도달 시 `position` 테이블 값이 중복 반영되는 문제

#### 원인 분석

여러 인스턴스가 동일 userId의 포지션에 대해 **Read-Modify-Write를 동시에 수행**하면서 경쟁 조건(Race Condition) 발생. Kafka 파티션 라우팅만으로는 인스턴스 재배정 과도기에 완전한 배타성 보장 불가.

#### 해결 방법

`lock:position:{userId}:{symbol}` 키로 **Redis 분산 락** 적용(timeout 5초, 최대 3회 재시도). Kafka userId key 기반 파티션 라우팅과 결합하여 **논리적 순서 + 물리적 배타성** 이중 보장.

#### 결과

멀티 인스턴스 환경에서 포지션 중복 계산 문제 완전 해소. `position` 테이블 정합성 확인.

### 🔴 트러블슈팅 #3 — api 프로필에서 Kafka Listener 중복 활성화

#### 문제

`profile=api`로 실행한 인스턴스에 `@KafkaListener`가 함께 등록되어, 오더북이 없는 api 인스턴스가 `orders.in`을 소비하다 NullPointerException 발생

#### 원인 분석

Spring Boot 자동 설정으로 인해 프로필 구분 없이 `@KafkaListener`가 모든 인스턴스에 등록됨. api 인스턴스가 Consumer Group에 불필요한 소비자로 추가되어 매칭 로직 없이 이벤트 처리 시도.

#### 해결 방법

`@Profile("worker")` 조건부 빈 등록을 활용해 `KafkaListener` 컴포넌트를 **worker 프로필에서만 활성화**. api 프로필에서는 `KafkaProducerConfig`만 로드하도록 빈 명확히 분리.

#### 결과

api / worker 프로필 완전 분리. api 인스턴스의 Kafka 소비 시도 문제 해소. 역할 경계 명확화.

## 💡회고 및 배운 점

## 기술적 깨달음

**"이벤트 드리븐"은 단순히 Kafka를 쓴다는 의미가 아님을 체감**

`orders.in → trades.executed → risk.commands`로 이어지는 이벤트 계약을 설계하며, 서비스 간 결합도를 낮추면서도 비즈니스 흐름을 보장하는 것이 얼마나 섬세한 작업인지 직접 경험했습니다. 특히 at-least-once 보장 환경에서 Consumer 멱등성 설계가 선택이 아닌 필수임을 깨달았습니다.

**원장(Ledger)을 SSOT로 두는 설계의 힘**

`account_balance`를 신뢰의 기준으로 두었다면, 대사 실패 시 "어떤 게 맞는 숫자인지" 판단할 기준이 없어집니다. `ledger_entry`를 불변 기록으로 유지하고 Projection을 검증 대상으로 두는 설계 덕분에 장애 분석과 재처리 로직이 단순해진다는 것을 실제 구현을 통해 확인했습니다.

**Write-behind는 양날의 검**

100건 단위 Bulk Update로 DB I/O를 획기적으로 줄였지만, 메모리 유실 시 미반영 데이터가 생길 수 있는 리스크도 함께 존재합니다. 이 트레이드오프를 인식하고 설계 문서에 명시하는 습관의 중요성을 배웠습니다.

## 협업과 설계에서 배운 것

- **이벤트 계약(Event Schema)의 사전 합의**가 협업 생산성을 좌우합니다. `orders.in`, `trades.executed` 스키마를 초기에 명확히 정의한 덕분에 매칭 파트와 리스크 파트가 독립적으로 개발을 진행할 수 있었습니다.
- **"기능이 동작한다"와 "시스템이 검증 가능하다"는 다른 수준의 목표**임을 깨달았습니다. 전체 파이프라인이 동작하는 것을 넘어, `recon_diff = 0`을 실제로 확인하는 검증 가능한 구조를 목표로 설정했습니다.
- **Kubernetes All-in-K8s 데모 환경 구축**을 통해 포트폴리오의 재현 가능성이 얼마나 중요한지 깨달았습니다. 코드만 보는 것이 아니라 직접 실행해서 확인할 수 있는 환경을 만드는 것이 차별점이 됩니다.
